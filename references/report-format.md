# 群聊总结报告格式规范

导出完成后，先通读导出目录中的 `messages.txt`（全部消息，分批读完，不得只读开头），
再按本规范在同一目录写 `summary.md` 与 `report.json`，最后运行 render 生成 HTML/PNG。

## 一、消息引用规则

- 每条消息有稳定 ID：`m<local_id>`（如 m95），见 messages.txt 每行开头 `[m95|10-28 14:02|发送人]`。
- 每个重要结论、待办、事实陈述必须关联实际存在的消息 ID，格式 `[m95]` 或 `[m90–m98]`。
- 引用前核对：该 ID 必须在 messages.json 中存在，且内容确实支持对应结论。禁止编造 ID。

## 二、summary.md 结构模板

```markdown
# <群名> · 群聊总结

**统计窗口**：<start_time> ~ <end_time>（Asia/Shanghai，含起点不含终点）
**消息量**：<N> 条 · **发言人数**：<N> 人 · **群成员**：<N> 人
**数据范围说明**：仅覆盖本机微信客户端已同步到本地的消息，不代表该群完整历史。

## 概览
（一段话：群内主要在讨论什么、谁是主要发言者/答疑者、整体氛围）

## 主要话题与讨论结论
### 1. <话题名> [m..–m..]
- 经过（带引用）……
- **结论**：……（标注是"已确定的结论"还是"某人的观点/建议"）

## 待办事项
| 事项 | 负责人 | 时间要求 | 当前状态 |
|---|---|---|---|
| … | …（未明确就写"未明确"） | … | …（带消息引用） |

## 已解决 / 已确认事项
- …… [m..]

## 尚未解决的问题
- …… [m..]

## 其他信息
- 分享的文章/视频链接、入群等系统事件、未解析的多媒体数量说明

## 口径说明
- 本报告仅覆盖本机已同步消息；……
```

## 三、report.json Schema

```json
{
  "overview": "一段概览",
  "topics": [{"title": "", "summary": "", "conclusion": "", "msg_ids": ["m90"]}],
  "todos": [{"item": "", "owner": null, "due": null, "status": "", "msg_ids": []}],
  "resolved": [{"item": "", "msg_ids": []}],
  "open_questions": [{"item": "", "msg_ids": []}],
  "other": "其他信息（可为空字符串）",
  "caveats": ["口径与注意事项列表"]
}
```

- `owner`/`due`/`status` 无信息时填 `null`（HTML/PNG 渲染为"未明确"），禁止自行补充。
- 所有 `msg_ids` 必须存在于 messages.json。

## 四、口径规范（必须遵守）

严格区分，不得混淆：
- **建议 ≠ 决定**：有人提出建议，除非有明确确认消息，否则写"建议"。
- **收到 ≠ 同意**："收到/好的/谢谢"只表示收到。
- **同意 ≠ 执行完成**：同意的方案在未完成前写"已确认待执行"。
- **群内观点 ≠ 已核实事实**：讲师/群友的答复标注为观点；宁可写"存疑可核"也不编造。
- 慎用"最/唯一/第一"等绝对化表述。
- 没有明确负责人或截止时间的待办，写"未明确"。

## 五、多媒体消息处理

- 图片/视频/语音/表情只有类型标记，**禁止描述其内容**（如"图中展示了……"）。
- 语音仅当消息内嵌转写文本时（messages.txt 中显示 `[语音转写] …`）才可引用其内容，并注明来自转写。
- 在"其他信息"中说明未解析多媒体的数量。
